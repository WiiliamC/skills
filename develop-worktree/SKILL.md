# Worktree 开发流程

以当前对话维持需求、进度和授权，不创建流程状态文件。继续任务无需重新调用本 skill。完整计划留在对话中，单次变更日志只记录必要事实。正常流程持续到合入、归档和清理完成；暂停、取消或阻塞时如实报告未完成部分。

## 调用、依赖与授权

- 讨论或修改本 skill 不表示启动工作流。仅显式调用；保留计划确认和人工验收，不因使用默认脚本而跳过。
- 调用授权创建任务 worktree、开发、使用 `develop_by_subagent`、`review-and-commit`、`improve-docs` 和必要时的 `resolve-merge-conflicts`，以及本任务的提交、归档与清理。不包含 push 或覆盖已有产物。
- 首先查找并读取上述依赖 skill 的实际文件；依赖或子代理能力缺失时说明并等待处理，不静默替换为主代理开发或跳过审查。跨仓库调用时明确传递实际工作目录和范围，不依赖继承的 cwd。
- 计划确认后才实现。人工验收通过即授权完成合入前文档检查后合入、归档和清理，无需另问是否合入。`improve-docs` 的具体建议仍按其规则获得批准；不能把验收通过当作批准未知文档修改。
- 冲突处理向 `resolve-merge-conflicts` 显式传递已获授权的实施范围：可兼容保留双方意图的修复直接实施；涉及需求取舍时等待用户决定。不能扩大为未确认的新行为。
- 遵循目标仓库适用的 `AGENTS.md`、环境权限和提交规范。没有提交规范时使用英文 `{type}: description`，合入提交使用 `merge: description`。

## 提问与等待

需要需求取舍、计划确认或人工验收时，提供具体方案和依据，再使用当前环境允许的提问工具。需要明确授权时，仅使用支持该用途的工具；没有可用工具则在 final 提出简洁问题并等待下一轮。链接并引用本 skill 中对应的确认要求。不把超时、空回答或预选项当作确认，不重复已有授权。当前环境处于 Plan mode 时仅规划，不以本流程覆盖模式限制。

## 1. 探索与澄清

读取 [规划参考](references/plan-mode.md)，探索相关实现、README、测试和仓库约定，明确目标、范围、限制和验收标准。参考中的工具使用方式以本 skill 和当前环境限制为准。

确定仓库绝对路径和集成分支：优先用户指定、项目明确约定，其次本地可解析的远程默认分支所对应的本地分支，再尝试本地唯一的 `main` 或 `master`。多个候选或无可靠候选时询问，不自动 fetch、切换用户分支或 stash。确定检出集成分支的工作目录，合入前若尚无该目录则先澄清集成位置；不把当前任意分支当作合入目标。

## 2. 创建 worktree 与需求记录

按 [脚本选择与默认接口](references/worktree-scripts.md) 分别选择创建、删除入口。项目实现存在但失败时排查原因，不用默认实现绕过项目检查。

任务分支使用简明语义名称，默认由小写字母、数字、下划线组成，例如 `feat_search`；检查分支、目录和日志不重名。默认脚本从已确认的集成分支创建，默认位置为仓库旁 `<仓库名>.worktrees/<branch>`；项目脚本按自身约定使用。运行前确认其实际基线；若脚本只能从当前 HEAD 创建，就从检出集成分支的目录运行，不悄悄改变基线。

日志沿用项目的单次变更记录约定；没有约定时使用 `docs/changes/YYYY-MM/<branch>.md`。月份取创建时本地月份，跨月继续原文档，先写需求与验收标准。日志的日期、命名等默认值只属于此流程，不要求写入项目规则。

后续代码、配置、测试、日志和开发产物写入任务 worktree；对子代理明确绝对路径和编辑边界。最终集成和归档才写入对应目标目录。

## 3. 确认计划并开发

按规划参考提供完整 `<proposed_plan>`，包括方案、关键设计、修改范围和验证方式，取得用户明确确认后执行。实质需求或设计变化重新确认，常规实现选择自行处理。

调用 `develop_by_subagent`，传递确认后的计划、需求、验收标准、任务目录和必要上下文，由子代理实施、主代理验收。更新简短日志，记载最终实现、关键决策及原因、实际验证和遗留问题。

长期规范写入适用 `AGENTS.md`；当前用法与契约写入模块 README 或已有设计文档，按 `maintain-docs` 维护。算法实验、基准和详细证据通过链接引用，测试通过不能代替效果结论。

## 4. 审查提交与人工验收

在任务目录调用 `review-and-commit`，显式限定本任务本轮的 staged、unstaged 和相关 untracked 改动，不能顺带提交其他工作。提交前日志已有开发总结和验证依据；审查失败继续修复，不视为通过。

审查后补充实际审查、修复和验证结果，不预填未知结果或本提交 hash。再次改代码需重新审查、验证。展示最终提交、待提交的事实性日志补充、验收步骤、预期结果、产物和已知问题，等待人工验收。说明通过后完成文档检查即直接合入。

验收不通过在原分支和日志迭代；实质方案变化重新确认。通过则记录验收版本。用户明确要求先合入时记录验收延期，保留用户需要的环境，不宣称验收通过。

日志补充在合入前统一整理：最后提交属于本任务、未发布且未被其他工作依赖时，仅事实性日志可 amend 并保留提交信息；否则集中新增日志提交，不改写共享历史。说明 amend 前后对应关系。仅事实性日志变化沿用已有代码审查和验收，实际行为变化重新验收。

## 5. 合入前文档检查

在任务目录调用 `improve-docs`，提供需求、实际改动、审查与验收结论，检查受影响文档和新契约，不扩大为全库审计。无可靠更新点时记录无需更新；有建议时展示具体内容并按依赖规则获得批准，只实施获批项。

修改后按前述规则审查提交。仅说明变化沿用验收；涉及代码或已确认契约变化，先澄清并回到开发和必要验收。待答复不能视为批准。

## 6. 集成与合入

满足验收或明确先行合入授权、文档检查完成后，展示最终摘要、验证与验收结论、遗留问题和归档清单，直接继续。

如果任务分支未包含集成分支最新提交，在任务目录合并集成分支。冲突按调用与授权规则处理；需求不兼容时询问具体取舍。无论是否有文本冲突，都验证新增集成结果，更新日志；集成分支没有新增提交时跳过重复同步验证。本集成步骤不再次调用 `review-and-commit`；影响已验收行为时重新人工验收，新增范围先取得确认。

核对集成目录仍检出目标分支且 HEAD 与刚验证的基线一致。用户改动确认不会受影响时原样保留，无法确认时暂停；不自动 stash 或覆盖。在集成目录使用 `git merge --no-ff <branch>`，提交正文引用变更日志并简述结果。基线再次变化或产生冲突时回到任务目录处理，不在集成目录直接修复。

## 7. 归档与清理

确认任务已合入指定分支，停止并发编辑。由主代理检查本任务进程，定向停止已结束用途的验收服务或测试；需继续运行时保留 worktree。脚本不杀进程。

检查未提交、未跟踪及 ignored 内容，逐项判断，不按目录名自动丢弃。按已展示清单复制重要产物到项目约定位置，保留来源，核验目标完整性（通常逐文件 SHA256），不自动覆盖或加入 Git。新发现的重要产物补充说明后处理；日志记录源、目标及验证方式，持久引用采用归档目标。

调用选定删除入口的检查模式。默认脚本完整列出 ignored 文件，包括缓存和链接；归档或确认可丢弃后才使用 `--artifacts-reviewed`，该选项不能绕过其他检查。宿主进程检查和最终删除必须在宿主执行，沙箱内空进程结果不证明无人占用。失败时保留现场，不拼接强制删除绕过检查。清理后核对目录、Git 注册、任务分支与归档结果。

最终报告合入提交、日志路径、验收、归档和清理结果。不为写入最终 merge hash 再新增提交。

## 日志内容

日志包含创建时间及时区、任务分支、需求与验收标准、最终实现和必要决策、实际验证与审查、人工验收、结论、遗留问题和相关入口。按任务组织，不固定空章节，不收录完整计划、任务清单、对话或原始运行日志。未知事实标记未验证，重要需求变化保留简短修订说明；详细历史只维护一份，其余链接引用。
