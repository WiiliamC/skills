# 审查、修复并提交

由当前主 agent 编排 review / fix subagent，不启动 Codex CLI 会话或脚本循环。调用授权审查、修复确认的问题，并在通过后调用 [quick-commit](../quick-commit/SKILL.md) 提交；不自动 amend 或 push。默认提交全部 tracked 改动及非忽略新文件，包括已有工作区改动；用户明确限定文件时遵从其范围，其他改动保留。

## 1. 固定范围

确定目标仓库绝对路径、用户需求、约束及适用仓库指令。开始时选择一次范围，在后续修复和当前对话内继续任务时沿用，不因工作区变化重新自动选择：

- **changes**：默认存在 staged、unstaged 或非忽略 untracked 文件时选择。审查 HEAD 到工作区的全部目标改动，覆盖暂存、未暂存及新文件内容。
- **branch**：默认没有未提交改动时选择。用户未指定基线时查本地 main，缺失再查 master；固定起始 merge-base，审查该基线到当前分支的提交及后续工作区修复。基线或共同祖先缺失时停止，不猜测、不自动 fetch。
- 用户明确指定的范围或基线优先。提交候选必须全部经过审查；若用户只要求审查部分内容，不把其余工作区改动带入提交。

确认 [审查流程](../review-changes/references/review-workflow.md)、其引用的官方 review 提示词及 simplify-changes、quick-commit 均可读取，且可以启动独立子代理。缺少依赖或委派能力时报告未完成，不静默降级为主 agent 实现。

## 2. 审查、复核、修复

使用 [交接范本](references/agent-briefs.md) 显式传入上下文。每轮依次进行，不让 review 与 fix 并发读写同一目标：

1. 等待开发、修复代理和会写文件的 hook 完成。修复阶段按仓库要求完成格式化及必要验证后再进入审查；审查不运行会修改文件的格式化命令。
2. 启动一个新的 review subagent；支持时用 `fork_turns="none"`，沿用当前模型和推理配置。要求读取上述审查流程，完成缺陷及简化审查；只读、不提交、不再委派。本流程以实际内容复核替代参考流程中可选的内容指纹检查，交接时明确这一覆盖规则。直接使用其参考流程，不调用会再启动子代理的 review-changes 主入口。
3. 主 agent 对每项建议复核证据、触发条件、影响与用户意图，记录采纳、驳回或待补证及简短原因。不重复整套审查；事实不足时让本轮审查代理补证或做定向检查。缺陷和可操作、保持功能的简化建议均处理；改变需求或功能范围的建议先取得用户取舍，不自动执行。
4. 有确认问题时，交给一个 fix subagent，明确允许修改的绝对路径、问题证据、必须保留的契约和验证要求。修复代理只处理确认问题及必要的相关调整，不提交、不推送、不再委派。主 agent 不替代修复代理实施。
5. 等待修复与 hook 完成，主 agent 检查实际 diff、问题是否解决、相关验证及范围是否守住。失败则让修复代理继续；符合要求后回到第 1 项，对固定的完整范围重新审查，不能只检查上一轮修补片段。

向下一轮传入已解决问题与已驳回建议及理由；没有新证据时不重复提出已驳回项，有新证据可以重新评估。不设固定轮数。同一问题反复无法解决、建议互相矛盾而无法裁定、内容持续变化或必要验证受阻且无法继续时，停止并报告未完成、剩余问题和所需条件，不提交。

## 3. 通过与提交

完整审查已完成、主 agent 已复核所有建议且没有确认的待处理问题时通过；没有证据的建议可以驳回，不能把审查不完整当作零问题。

审查期间记录起始 HEAD、范围和实际阅读的内容；审查代理结束及 hook 完成后，主 agent 核对实际 diff 和新文件内容。仅看 `git status` 不足以确认内容未变。不计算自定义工作区指纹、不建立快照交接或持久状态文件。审查后若有内容修改，回到审查步骤，由新 review subagent 复核受影响内容和关联契约，确认未受影响部分仍有效；HEAD 或基线发生意外变化时先重新确定范围，不能沿用旧通过结论。

通过后由当前主 agent 读取并执行 quick-commit skill，明确传入本流程已确定并审查通过的提交范围，不再委派提交；quick-commit 沿用此显式范围，不扩大或自行改选。提交前及暂存后的候选内容必须仍是审查通过的内容；发现新增或变动内容时先回到审查，不能由快速提交直接带入。

提交失败时检查 Git 实际状态。若 hook 修改内容，重新检查并审查受影响内容后再提交；已产生提交时报告真实结果，不盲目重试。未修改内容的环境失败解决后可沿用仍有效的审查结论。若提交已成功，但实际提交包含 hook 等引入的未审查差异，明确报告并将这些提交差异纳入补充审查，不能以新 HEAD 上工作区干净作为通过依据；必要修复创建新提交，不自动 amend 或重写已创建的提交。保留现场，不绕过 hooks、签名或权限要求。

## 结果与继续

简要报告固定范围、审查与修复结论、主要采纳或驳回理由、实际验证及限制、提交短 hash 和 subject；无改动时报告无改动可提交。当前对话内继续沿用已有范围与结论；新会话重新核实当前内容，不实现日志恢复协议。

旧脚本、CLI 参数、轮数上限、service tier / 提交消息模型参数和 `--resume` 已移除。用自然语言指定仓库、changes / branch 范围和基线，不调用旧入口。
