# 对话复盘与技能改进

根据当前可见对话，判断已有 skill 是否需要改进。先提供可审批的具体建议，再实施获批修改；没有可靠改进点时允许得出“无需更新”。

## 选择目标与证据

- 用户指定目标时只检查指定 skill；否则检查当前对话实际使用、尝试使用，或被明确指出存在问题的 skill。仅在技能列表出现或调研中被提及，不算需要检查的目标。
- 从对话和已知路径定位技能，读取其 `SKILL.md`；仅在相关时读取脚本、引用和 `agents/openai.yaml`。不遍历整个技能库，不读取历史会话或生成经验数据库。
- 只使用当前可见对话中的用户纠正、实际结果和重复低效行为作为证据。无法定位文件或上下文不足时说明缺口，不猜测缺失内容。
- 先判断问题来源：技能指令遗漏或错误、配套资源缺陷、执行时未遵守已有规则、环境限制，或一次性要求。已有规则正确且足以覆盖问题时，不重复添加规则；环境限制只有形成已验证、可复用的处理方式时才考虑更新。
- 优先采纳用户明确表达的长期要求和已验证经验。用户最新明确要求优先于先前要求；不把推测、建议、泛泛赞许或单次成功升级为通用规则。保留项目和场景条件，不把临时偏好推广到所有任务。

## 提出建议并等待批准

逐项编号，给出：

1. **目标与位置**：skill 名称、文件及需要修改的段落或行为。
2. **依据与问题**：当前对话中对应的纠正或结果，以及现有内容为什么不足。
3. **具体修改**：拟替换、删除或新增的文字；脚本改动提供足以审批的具体逻辑或精简 diff。说明预期行为和适用条件。

建议优先合并、替换或删除问题内容，而不是不断追加经验章节。每项建议应能单独批准；相互依赖的改动合为一项。不要为每个目标强行凑建议。

提出建议后，明确请用户批准全部或指定编号，并停止，等待后续回复。批准前不修改文件，包括不提前写草稿、补丁文件或经验记录。初次调用、提前要求“直接改”或允许一般任务修改，都不能替代用户对本轮具体建议的批准。

没有可靠改进点时，简要说明无需更新及原因，结束本次检查，不索要无意义的批准。

## 实施获批修改

- 用户批准全部或指定编号后，直接执行对应建议，不重复请求同一批准。仅讨论建议、要求解释或回复含糊时，不视为批准。
- 用户调整建议时，先展示调整后的具体内容，再等待批准；新增或实质变化的建议也需另行审批。未获批项不实施。
- 修改前重读目标文件，检查是否与提出建议时一致，保留用户已有改动。无关变化不影响获批修改；若相关内容变化导致建议不再适用，先重新提出调整后的建议。
- 只修改获批涉及的文件和行为。保留技能名称、无关规则、调用策略和元数据；只有获批建议明确涉及这些内容时才修改。引用及调用关系随对应获批改动保持一致。
- 将经验整合进合适的指令或资源，清除对应的重复和冲突，不新增原始对话存档。公开文件中使用相对路径、环境变量或通用占位符，不写入凭据、私人机器信息或运行日志。
- 文件不可写或操作被拒绝时说明限制，按环境权限要求处理；不偷偷修改另一份副本并宣称原技能已更新。不自动提交、推送或发布。

## 验证与汇报

- 检查修改是否符合获批建议，描述、正文、引用和调用策略是否一致，是否引入重复、冲突或过度泛化。
- 可用时使用技能格式验证器（如官方 `quick_validate.py`）；涉及 `agents/openai.yaml` 时另行检查 YAML 和字段。格式通过不等于行为有效。
- 仅改文字时检查内容一致性，并用对应对话案例推演新指令是否修正问题、保留原有行为；修改脚本时执行相关行为验证。验证需要额外权限或实际外部副作用时遵守环境授权范围。
- 报告已完成的建议编号、修改文件、验证结果及未能验证的部分。区分静态检查、案例推演和实际执行，不能把未运行的行为测试说成已通过。
