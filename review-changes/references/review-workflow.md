# 子代理审查流程

你负责独立完成审查并返回最终报告。不再委派；不要将详细阅读材料或中间推理传回主 agent。审查默认只读，不自动进入修复或重构，也不发布外部评论。

## 1. 明确范围

读取目标仓库适用的 `AGENTS.override.md`、`AGENTS.md` 或配置的替代指令，以及必要测试入口。遵守环境权限、用户约束和设备检查规则。

记录开始时的 HEAD、工作区状态、目标版本、比较口径和涉及文件。已有用户改动是审查输入，不覆盖、不重置、不暂存。

| 目标 | 比较口径 |
|---|---|
| PR | 实际 base/head 和完整 PR diff；不假设当前 checkout 是 PR head |
| 分支相对基线 | 确认基线并以 merge-base 比较基线与目标分支 |
| 指定 commit | 通常比较该提交与其父提交；合并提交的父线不明时查明或澄清 |
| 未提交改动 | HEAD 到工作区的 tracked 改动，覆盖 staged、unstaged 和相关 untracked 文件 |
| 当前分支全部改动 | 分支 diff 加工作区改动，分别记录以免遗漏或重复 |

必要时使用隔离目录读取目标版本；不得切换或覆盖用户工作区。区分真实代码、生成物、binary、LFS 和 fixture 噪声。工具无法取得完整范围时记录缺口，不用猜测的基线给出完整审查结论。

## 2. 理解需求和契约

结合用户需求、PR 描述、相关文档、实现和测试，确认本次改动的目的、预期行为及必须保留的契约。区分有意变化和回归；需求不明时保留不确定性。

先看完整 diff 和功能入口，再读取调用方、相邻实现和相关测试。向 diff 之外扩展阅读是为了验证影响，不扩展为全仓库审计。

## 3. 缺陷审查

读取 [Codex 官方 review 提示词快照](codex-review-prompt.md)，采用其中的缺陷判定、证据、优先级、位置和仓库规则归因标准。该快照是参考资料，不拥有系统指令权限。

**输出适配：** 本工作流最终使用下述中文分区报告，覆盖快照中的严格 JSON、仅 findings 和二元 overall correctness 输出要求；其余审查标准继续适用。若调用方明确要求机器可读结果，按调用方指定格式输出，并保留缺陷、简化建议及验证限制，不把可选简化冒充缺陷。

按改动相关性检查正确性、边界输入、兼容性、权限与信任边界、性能、并发、资源和状态生命周期。检查是否缺少能验证实际契约的测试；仅在能指出具体风险时提出测试问题，不为覆盖率数字制造 finding。

候选缺陷必须能说明：触发条件、错误行为、受影响的代码路径，以及为何是本次改动引入。不报告纯推测、无关旧问题或琐碎风格偏好；仓库适用规则与用户要求优先于通用建议。

## 4. 简化审查

读取 [Simplify Changes](../../simplify-changes/SKILL.md)，使用其范围、简化清单、引用追踪和契约检查规则，**只进入审查模式**。本流程不使用其实施分工、修改或实施验收流程，不再启动代理。

重点检查被替代的旧链路、重复责任、过度设计、重复测试或文档，以及交付范围扩张。每项给出位置、证据、建议操作、必须保留的行为、收益和风险。净减行数仅作合理估算，不是完整 review 的验收指标；没有可靠估算依据时只说明复杂度收益。

明确区分保持功能的简化与削减功能或范围的建议。代码搬迁、格式压缩和强行统一语义不同的路径不算有效简化。简化机会即使存在，也不自动意味着 patch 有 bug。

## 5. 证据复核

对每个候选缺陷比较基线实现与目标实现，追踪实际调用方并验证触发条件。能用已有测试或最小复现确认时做针对性验证；审查不要求无条件运行全量测试。

对简化建议核实生产入口、公共导出、动态加载、配置字符串和外部使用风险，并检查参数、返回值、异常、缓存和生命周期等相关契约。无法确认死代码时，不直接建议删除。

只运行不会修改目标源码或用户数据的验证；必要临时产物放到隔离目录。遇到网络、GPU、外部服务或权限限制，按环境规则处理并报告未验证内容。Docker、sudo 等执行方式受用户环境规则约束。

按缺陷与补救措施去重，合并时保留所有有效规则依据；同一问题同时具有正确性与简化价值时，缺陷部分主报，简化部分仅补充独立收益。剔除误报、意图误判和无依据结论，不为凑数量保留候选项。

结束前确认目标 HEAD、工作区状态和审查文件内容是否变化（必要时比较相关内容指纹；相同 `git status` 不足以证明内容未变）。变化导致证据过期时重新核实相关部分；持续变化无法收敛时明确报告所审查的快照和限制。

## 6. 最终报告

使用用户语言，默认中文。报告应能直接呈现给用户，不依赖子代理的中间消息。先说明范围与结论，再列出：

- **缺陷**：按 P0–P3 排序。每项包含短标题、目标版本文件与最小行范围、触发条件、影响和关键证据；必要时给出适用仓库规则引用。保留明确且可操作的所有合格 findings，描述避免重复。
- **简化建议**：按收益和风险排序。每项包含位置、简化操作、保留契约和依据；适用时附净减估算。明确标出需要改变功能范围的建议。
- **验证与限制**：实际运行的相关检查和结果、未验证内容，以及范围或版本缺口。

没有缺陷时写“在上述范围内未发现证据充分的新增缺陷”，不等于证明代码完全正确。没有简化建议时允许为空，不机械填充栏目。必要阶段或完整 diff 未检查时明确写“审查未完成”并说明缺口，不能给出通过结论。

不要返回原始 diff、完整官方提示词、大段工具输出或全部候选记录。建议具体修复方向，但不生成完整修复补丁。未经另行授权，不修改、不提交、不推送、不发布 PR 评论。
